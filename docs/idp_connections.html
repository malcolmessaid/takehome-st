Systems

How IdP access reaches an application

A person has one IdP account. The account joins groups, groups can sit inside other groups, and an assignment grants an application to a group (or, in principle, to a single account).
Only memberships and assignments with revoked_at IS NULL count as current access.

How Google Workspace access reaches a Drive file

Same shape as the IdP. A person has one Google account, which joins Workspace groups, and a Drive permission shares a file with a group or directly with one account. Owning a file is a separate way in, with no permission row.
A Google account links to the IdP only through person_id. Its ID (gwa_…) never matches an IdP ID (idpa_…).
A permission's principal_type can be account, group, domain (the whole company) or external_email (outside the company). This data only has account and group.
Drive permissions can also expire: check expires_at as well as revoked_at. There's no parent-folder column, so permissions don't visibly pass from a folder to the files in it.

How GitHub access reaches a repository

A person has a GitHub account, which joins teams, and a team gets a permission on a repository. A repository can also be shared directly with one account as a collaborator.
Org membership is the account being in the GitHub organisation at all (946 rows, 915 current). Most come from IdP sync (idp_scim), and 82 current ones were added by hand.
Teams don't nest here. A team with source_idp_group_id is fed by IdP group membership, which is how IdP groups end up granting repository access.
Collaborator grants can expire (expires_at), and their approval reference may be missing.
